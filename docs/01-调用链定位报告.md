# 01 · 调用链定位报告

> **性质**：只读分析报告，不含任何代码改动。
> **对象**：`zuma-demo/`（基于开源项目 [jamiely/tsuma](https://github.com/jamiely/tsuma) 的快照）。
> **行号基准**：改造前快照。改造后行号会漂移，请以函数名为准。
> **对应作业任务**：调用链定位（Agent 只输出报告，不改代码）。

---

## 1. 结论：三个入口

| 入口 | 语义 | 权威定义位置 | 写入/触发位置 |
|---|---|---|---|
| **关卡定义入口** | "当前玩哪一关、这一关长什么样" | `src/boards/boards.ts:109` `buildBoards()` | `src/game.ts:144` `loadBoard()` |
| **游戏结束入口** | "本局什么时候算结束" | `src/types.ts:208` `Game.boardOver` | `src/movement/movement.ts:436`（`lost`）、`src/game.ts:206`（`won`） |
| **重置 / 重试入口** | "怎么把这一关重新开始" | `src/game.ts:484` `resetBoard()` | 由 `src/game.ts:392` `stepBoardOver()` 自动调用 |

一句话：**关卡是数据、结束是一个字符串字段、重试是一个内部函数**——三者都没有对外接口，这也正是本次改造要补的地方。

## 3. 关卡定义入口（入口一）

### 3.1 数据形态

```ts
// src/types.ts:79-85
interface Board {
  name: string;              // 显示名，如 "1-1 Spiral"
  launcherPosition: Point;   // 青蛙炮台位置
  paths: WaypointPath[];     // 球链路径（可多条）
  ballCount?: number;        // 本关总球数，缺省 100
  colors: Color[];           // 本关可用颜色
}
```

`Game.boards` 是 `Record<BoardName, Board>`，**全部关卡在启动时一次性构建**（`boards.ts:109-236`），没有任何按需加载或远程配置。

### 3.2 选择与装载

| 步骤 | 位置 | 作用 |
|---|---|---|
| ① 读选关参数 | `src/main.ts:55` | `params.get('board') as Game['currentBoard'] \|\| "board11"` |
| ② 构建全部关卡 | `src/boards/boards.ts:109` | `buildBoards(bounds)`，50+ 关硬编码 |
| ③ 单关定义 | 例：`src/boards/board11.ts:5` | `board11(bounds)` → `name:"1-1 Spiral"`, `ballCount:30`, 螺旋路径 |
| ④ 装载当前关 | `src/game.ts:144-158` | 写 `launcher.position / paths / ballsLeft`，`chains = paths.map(createChain)` |
| ⑤ 清空上局残留 | `src/game.ts:146-149` | 清 effects、复位速度/发射间隔 |

### 3.3 选关 / 解锁现状（重要）

- **没有选关界面**：全仓库无关卡列表 UI、无解锁进度、无 `localStorage`。
- **唯一"选关"入口就是 URL**：`?board=board21`。
- **通关会自动进下一关**：`src/game.ts:396` → `nextBoard()`（`:402-470`，按硬编码数组顺序取下一关）。
- 结论：作业表里"去掉关卡选择/解锁"在本项目中**退化为两件事**——删 URL 参数、切断自动跳关。工作量远小于表格预期。

### 3.4 演示关候选

| 关卡 | 球数 | 路径 | 适配度 |
|---|---|---|---|
| `board11`（默认） | 30 | 单条阿基米德螺旋（squash 1.5） | ★ 最贴合祖玛观感，改动量为零 |
| `board12`–`board15` | 30 | 同系列 | 需额外验证发射点 |
| `line` / `test` 系列 | 1 | 直线 | 验收最快，但不像正式关 |

## 4. 游戏结束入口（入口二）

### 4.1 状态只有一个字段

```ts
// src/types.ts:208-209
boardOver?: "won" | "lost";
boardOverSteps: number;
```

没有 `gameOver` 终态、没有 lives、没有 restart 按钮。`boardOver` 是"本关已结束"的唯一信号。

### 4.2 失败（lost）链

```
src/movement/movement.ts:429   到达最后一个 waypoint 后 dist < WAYPOINT_DISTANCE_DELTA
src/movement/movement.ts:433   chainedBall.waypoint = nextWaypoint   // = undefined
src/movement/movement.ts:436   game.boardOver = "lost"               ★ 唯一的 lost 写入点
src/movement/movement.ts:439   removeBall(chain, node)               // 撞洞那颗球被移除
        │
        ▼  下一帧
src/game.ts:200-203            step(): if (game.boardOver) { stepBoardOver(game); return; }
src/game.ts:392-394            stepBoardOver(): if (boardOver === "lost") → stepBoardOverLost()
src/game.ts:472-482            stepBoardOverLost(): boardOverSteps++
                                 ├─ === 1   → dispatch(BoardOverEvent)   // 只派发一次
                                 └─ > 300   → resetBoard(game)          ★ 自动重开
src/movement/movement.ts:42-59 期间 stepMovement 走 stepBoardOver()，把剩余球"加速吸收进洞"
src/game.ts:484-488            resetBoard(): boardOver=undefined; loadBoard(game)
```

**自动重开是本项目最容易踩的坑**：输了不弹结算，2.5 秒后（300 步 @2 步/帧）直接满血重开，和作业"结束后输入无效"的验收直接冲突。

### 4.3 胜利（won）链

```
src/game.ts:205-208    step(): if (boardWon(game)) { game.boardOver = "won"; return; }
src/game.ts:574-581    boardWon(): ballsLeft <= 0 且所有 chain 的 head/foot 均为空
        │
        ▼  下一帧
src/game.ts:392-400    stepBoardOver(): 非 lost 分支 → nextBoard(game) → loadBoard(game)
src/game.ts:402-470    nextBoard(): 按 boardList 顺序取下一关（board11 → board12 → …）
```

**胜利会静默切关**，同样不弹结算。若只锁"初始关卡"而不管这里，通关一局就会看到 1-2，等于没锁。

### 4.4 事件与音效现状

| 事件 | 定义 | 派发 | 音效 |
|---|---|---|---|
| `BoardOverEvent` | `types.ts:293-301` | `game.ts:475`（仅 lost，第 1 步） | `sounds.ts:15` 为 `undefined` |
| `GameOverEvent` | `types.ts:283-291` | **从未派发**（死代码） | `sounds.ts:13` 已有 `audioGameOver` |

改造时可以直接复用 `GameOverEvent`——音效管理器已经在监听它，派发即可发声，无需改音频代码。

### 4.5 结束后的输入现状（守卫审计）

| 位置 | 现状 | 结论 |
|---|---|---|
| `game.ts:170` `launchBall()` | `if (game.boardOver) return;` | ✅ 已挡住发射 |
| `game.ts:200` `step()` | boardOver 时仍调 `stepBoardOver()` | ❌ 仍在推进/自动重开 |
| `movement.ts:34` `stepMovement()` | boardOver 时走 `stepBoardOver()` 动画 | ⚠️ 球还在动 |
| `interface.ts:9-11` | click 直接 `launchBall`，自身无终态判断 | ⚠️ 仅靠 `launchBall` 兜底 |
| `renderer.ts:78-89` | 写死文案 "Whoops! Restarting the board." | ❌ 与"结束"语义不符 |

## 5. 重置 / 重试入口（入口三）

| 函数 | 位置 | 语义 | 能否当"再来一局" |
|---|---|---|---|
| `resetBoard(game)` | `game.ts:484-488` | 原地重置当前关（boardOver 清空、steps 归零、`loadBoard`） | ✅ **推荐**，模块私有，需导出包装 |
| `loadBoard(game)` | `game.ts:144-158` | 只装载数据，不清 boardOver | ⚠️ 需配合清 boardOver |
| `createGame(...)` | `game.ts:76-142` | 整局重建（新的 events、sound、boards） | ❌ 太重，会重建事件系统 |
| `setupNextGame(game, next)` | `game.ts:684-690` | 替换 game 对象并**置 `debug.stop = true`** | ❌ 会冻结渲染，仅限调试/回放 |
| `rewindHistory(game)` | `game.ts:675-682` | 从历史快照回退 | ❌ 调试专用 |

**结论**：作业要求"调用原重置逻辑"→ 用 `resetBoard()`，包一层 `restartGame(game)` 导出即可，不要走 `setupNextGame`。

## 6. 球链数据流（改造时的计分挂点）

```
loadBoard        → chains = paths.map(createChain)         // 每关每条路径 1 条链
step()           → stepMovement()   → stepChains()          // 沿 waypoint 推进
                 → handleCollisions()                       // 自由球撞入球链
                 → resolveMatches()  → { matches }          // ★ 消除判定在这里
                 → appendToChain()   → ballsLeft--           // 补球
                 → stepLauncher()                            // 剩余球少时换色
boardWon()       → ballsLeft<=0 && 所有链空 → won
```

- **消除数量**目前不对外暴露：`resolveMatches` 只返回 `{matches: boolean}`（`match.ts:6,78`）。计分需要在它的消除循环里累计被移除的节点数。
- 爆炸道具另有一条移除路径：`game.ts:344-372` `removeBallsFromExplosion()`。

## 8. 风险与边界

1. **没有分数系统**：`score` 需新增；分数无固定期望值（随机出球），测试只能断言"分数 = 消除数"或"> 0"。
2. **没有终态**：必须先把 `boardOver` 从"动画状态"改成"终态"，否则任务 3/4 无处挂钩。
3. **`pnpm build` 当前是红的**：`tsc` 报 2 个既存错误（`renderer.ts:473` 未使用 `drawImage`、`:479` 展开参数），与本改造无关但必须顺手修，否则无法提交。
4. **动态验收受限**：沙箱内 `vite` / `vitest` 依赖 esbuild 子进程，默认会被拦截（spawn EPERM）。
   改造过程中以"借用原项目依赖 + 重定向临时目录"的方式跑通了单元测试（90/90 通过；
   `renderer.test.ts` 因上游缺少 DOM 环境失败，属既存问题）。
   `pnpm dev` 的浏览器级验收仍需在开发机执行。
5. **无版本控制**：仓库快照无 `.git`，改造全程采用定点编辑、逐文件 `tsc` 自检，不使用整文件重写。
